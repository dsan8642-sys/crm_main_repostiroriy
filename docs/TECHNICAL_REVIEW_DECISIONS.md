# Technical Review Decisions

Этот документ фиксирует согласованные решения технического ревью. Исправления
выполняются строго по порядку. После завершения каждого пункта его статус
обновляется вместе с кратким результатом проверки.

## 1. Методы редактирования справочников

- **Проблема:** frontend использует `POST`, backend принимает `PATCH/PUT`,
  контракт расходится с реализацией.
- **Решение пользователя:** перевести frontend на `PATCH`, исправить контракт.
- **Статус:** исправлено.
- **Результат:** экран настроек использует `PATCH`; исполняемый контракт
  соответствует backend. Regression-тест подтверждает успешный `PATCH` и
  отклонение `POST`; production-сборка frontend проходит.

## 2. Доверие браузерному payload импорта

- **Проблема:** commit применяет изменяемые `status/resolved` без полной
  серверной перепроверки.
- **Решение пользователя:** серверный import batch; commit принимает `batch_id`
  и выбранные строки, повторно проверяет ограничения.
- **Статус:** исправлено.
- **Результат:** preview хранит исходные данные на сервере 30 минут; commit
  принимает только `batch_id` и `selected_indices`, повторно строит preview
  внутри транзакции, проверяет тип, владельца, срок действия и однократность.
  Подмена browser payload отклоняется, исходные строки очищаются после commit,
  а истёкшие batch удаляются штатной фоновой задачей.

## 3. Изменяемая цена исторического посещения

- **Проблема:** начисление использует текущую цену и валюту группы.
- **Решение пользователя:** фиксировать snapshot цены и валюты при создании
  занятия.
- **Статус:** исправлено.
- **Результат:** занятие сохраняет `price_minor` и `currency` при создании;
  миграция восстанавливает snapshot из существующего положительного списания,
  а при его отсутствии — из текущего тарифа группы. Начисление и отмена
  посещения используют только snapshot занятия и не смешивают валюты.
  Системные snapshot-поля исключены из обычного редактирования.

## 4. Финансовые последствия исторического импорта

- **Проблема:** импорт старых посещений расходует текущий абонемент или создаёт
  начисление.
- **Решение пользователя:** два режима; по умолчанию только история, отдельный
  подтверждаемый и аудируемый режим с финансовыми последствиями.
- **Статус:** исправлено.
- **Результат:** режим `history_only` используется по умолчанию и сохраняет
  посещение без ledger-списаний и денежных начислений; безопасная политика
  закрепляется на записи посещаемости и сохраняется при последующих изменениях
  статуса. Режим `apply_financial` фиксируется в server-owned batch, требует
  отдельного подтверждения при commit и сохраняет режим, результат и
  администратора в неизменяемом audit log.

## 5. Неполный release installer

- **Проблема:** installer не получает готовый frontend и не применяет миграции.
- **Решение пользователя:** неизменяемый CI-артефакт с `dist`; installer
  проверяет и использует этот артефакт. Обязательный backup/migration gate
  реализуется следующим пунктом.
- **Статус:** исправлено.
- **Результат:** после полного release gate CI собирает один commit-addressed
  deployment bundle с исходниками точного commit, готовым `frontend/dist` и
  встроенным `RELEASE_PROVENANCE.json`. Внешний manifest фиксирует SHA-256
  архива и списка файлов; для файлов frontend дополнительно проверяются
  индивидуальные SHA-256. Повторная запись bundle запрещена, GitHub artifact
  привязан к полному `github.sha`, а target-host installer и verifier
  поддерживают новый формат без отказа от старого source archive.

## 6. Непроверяемый backup evidence

- **Проблема:** release gate требует доказательства, которые штатные скрипты не
  создают.
- **Решение пользователя:** обязательный минимум: dump, SHA-256 и успешное
  тестовое восстановление; лишние формальные проверки удалить.
- **Статус:** исправлено.
- **Результат:** штатный dump создаёт sidecar SHA-256; restore verifier
  обязательно сверяет checksum, проверяет каталог backup и выполняет реальное
  восстановление во временную БД.

## 7. Удаление занятия вместе с бронированиями

- **Проблема:** занятие может каскадно удалить участников и лист ожидания.
- **Решение пользователя:** разрешить администратору принудительное удаление
  только будущего занятия без attendance/payroll, с показом последствий,
  усиленным подтверждением и аудитом.
- **Статус:** исправлено.
- **Результат:** DELETE требует `force=true` и точный ID занятия, допускает
  только будущее занятие без attendance/payroll и пишет состав последствий в audit.

## 8. Пустая цена новой группы

- **Проблема:** пустое поле превращается в `"undefined"` и блокирует сохранение.
- **Решение пользователя:** хранить `null` как «тариф не настроен»; до задания
  цены не создавать разовое начисление.
- **Статус:** исправлено.
- **Результат:** значение `null` остаётся состоянием «тариф не настроен» и не
  создаёт разовое начисление.

## 9. Аудит настроек от имени System

- **Проблема:** теряется идентификатор администратора.
- **Решение пользователя:** записывать реального администратора для всех ручных
  изменений; `System` оставить фоновым операциям.
- **Статус:** исправлено.
- **Результат:** настройки аудируются от имени авторизованного администратора.

## 10. Опасный rollback импорта

- **Проблема:** импортированные сущности удаляются без preview, усиленного
  подтверждения и аудита.
- **Решение пользователя:** безопасный rollback конкретного batch с preview,
  вводом batch ID, проверкой зависимостей и аудитом.
- **Статус:** исправлено.
- **Результат:** доступен preview отката, rollback требует точный ID batch,
  блокируется при появлении поздних зависимостей и аудируется.

## 11. Ложные дубликаты платежей

- **Проблема:** два одинаковых платежа клиента в один день считаются одним.
- **Решение пользователя:** необязательный `transaction/reference ID`; без него
  совпадение требует ручного решения администратора.
- **Статус:** исправлено.
- **Результат:** optional reference ID уникален; совпадение без него помечается
  как вероятный дубликат и требует явного подтверждения администратора.

## 12. Неявное округление денег

- **Проблема:** импорт молча изменяет сумму с лишними десятичными знаками.
- **Решение пользователя:** отклонять строку в preview при превышении точности
  валюты.
- **Статус:** исправлено.
- **Результат:** строки с избыточной точностью отклоняются уже в preview.

## 13. Неоднозначный тренер при импорте

- **Проблема:** совпадающее ФИО может связать посещение не с тем тренером.
- **Решение пользователя:** использовать ID, username или email; неоднозначное
  ФИО разрешать вручную в preview.
- **Статус:** исправлено.
- **Результат:** importer разрешает ID, username и email; неоднозначное ФИО
  требует уточнения.

## 14. Неограниченный XLSX

- **Проблема:** файл и все строки загружаются в память без ресурсных ограничений.
- **Решение пользователя:** максимум 5 МБ, 5 000 строк и 50 столбцов, ранняя
  проверка и потоковое чтение.
- **Статус:** исправлено.
- **Результат:** сервер ограничивает import до 5 МБ, 5 000 строк и 50 столбцов,
  XLSX читается потоково.

## 15. Жёсткий предел 2 000 записей

- **Проблема:** данные после лимита скрываются, фильтрация может быть неполной.
- **Решение пользователя:** серверная пагинация `page/page_size`, 50 строк по
  умолчанию, максимум 200; поиск, фильтры и сортировка до пагинации.
- **Статус:** исправлено.
- **Результат:** списочные admin API используют серверную пагинацию 50/200; frontend
  последовательно загружает все страницы, а фильтрация выполняется до пагинации.

## 16. Ослабленная парольная политика

- **Проблема:** принимаются пароли от 8 символов без проверки распространённых
  паролей.
- **Решение пользователя:** оставить текущую политику с минимумом 8 символов;
  риск принят.
- **Статус:** не исправлено; риск принят, изменение не требуется.

## 17. Drift API-контракта

- **Проблема:** документация методов и маршрутов не соответствует backend.
- **Решение пользователя:** OpenAPI как машинно-читаемый источник истины с
  CI-проверкой соответствия.
- **Статус:** исправлено.
- **Результат:** runtime OpenAPI 3.1 строится из фактических Django URL и доступен по
  `/api/openapi.json`; CI-проверка сверяет документацию и уникальность операций.

## 18. Остаточные упоминания прежнего low-code решения

- **Проблема:** действующие документы противоречат Django-only архитектуре.
- **Решение пользователя:** удалить все упоминания прежнего low-code решения из репозитория без
  архивного ADR.
- **Статус:** исправлено.
- **Результат:** в коде и документации отсутствуют упоминания прежнего low-code
  продукта; активный путь только Django + собственный frontend.

## 19. Общий отказ экрана настроек

- **Проблема:** ошибка одного endpoint скрывает результаты остальных запросов.
- **Решение пользователя:** независимая загрузка разделов с локальной ошибкой и
  повтором.
- **Статус:** исправлено.
- **Результат:** независимые запросы настроек используют `Promise.allSettled`;
  успешные разделы остаются доступны при ошибке соседа.

## 20. Частичная массовая выдача согласий

- **Проблема:** операция может применить часть согласий и показать только общую
  ошибку.
- **Решение пользователя:** разрешить частичное выполнение, но возвращать и
  показывать результат каждой записи.
- **Статус:** исправлено.
- **Результат:** batch возвращает результат каждой записи и HTTP 207 при частичном
  успехе; frontend показывает конкретные неуспешные согласия.

## 21. Мёртвый параметр `AllowOpsCritical`

- **Проблема:** параметр не меняет поведение health-check.
- **Решение пользователя:** удалить параметр; critical всегда блокирует release
  gate, диагностику отделить.
- **Статус:** исправлено.
- **Результат:** параметр удалён из health-check; critical состояние не имеет
  обходного флага.

## 22. Wildcard-зависимости модуля настроек

- **Проблема:** views скрыто зависят от приватных функций большого `support.py`.
- **Решение пользователя:** разделить access, audit и serializers на небольшие
  модули, использовать явные импорты.
- **Статус:** исправлено.
- **Результат:** access, audit и serializers вынесены в отдельные модули с явными
  импортами; дублирующие реализации удалены из views.

## 23. Тариф индивидуальных и split-занятий

- **Проблема:** конкретное занятие не хранит собственную цену, поэтому нельзя
  надёжно назначить разные тарифы для `individual` и `split` и безопасно
  переопределить их до проведения.
- **Решение пользователя:** использовать стандартную цену и валюту по типу
  занятия с копированием в snapshot при создании. Администратор может
  редактировать snapshot только до `start_at`; после начала цена блокируется.
  Цена `split` задаётся за всё занятие и делится поровну. При неявке каждому из
  двух записанных клиентов сохраняется половина; если клиент один, начисляется
  только половина. Суммы, не делящиеся поровну в minor units, округляются вниз
  для каждого участника, допустима разница в одну минимальную денежную единицу.
- **Статус:** исправлено.
- **Результат:** занятие хранит snapshot цены и валюты, тариф задаётся по типу,
  редактирование блокируется после начала, split делится поровну с округлением вниз.

## 24. Неудобные единичные шаблоны расписания

- **Проблема:** текущий шаблон описывает одну тренировку и требует отдельных
  операций для каждого дня, типа занятия и группы; копирование большого периода
  трудоёмко.
- **Решение пользователя:** заменить единичные шаблоны недельным планом группы и
  добавить мастер копирования фактического расписания. В мастере можно независимо
  выбрать групповые, индивидуальные и split-занятия. Копирование сохраняет день
  недели, время, тренера, локацию, длительность и вместимость; для individual
  сохраняется клиент, для split — назначенные участники. У групповых занятий
  состав клиентов заново определяется группой. Новые individual/split получают
  актуальный тариф типа и новый snapshot цены. Не копируются attendance,
  списания, платежи, payroll, отмены и временные замены. Изменение недельного
  плана влияет только на новые генерации. При более длинном целевом периоде
  лишние недели остаются пустыми. Старые шаблоны автоматически объединяются по
  группам, конфликты разрешаются по отчёту. Все массовые операции используют
  preview, проверку активных клиентов и тренеров, контроль конфликтов, аудит и
  защиту от дублей.
- **Статус:** исправлено.
- **Результат:** добавлены недельные планы с несколькими слотами и отдельный
  preview/commit мастер копирования периода; старые шаблоны мигрируют в планы групп.

## 25. Ручной расчёт времени окончания тренировки

- **Проблема:** формы требуют вручную вводить `start_at` и `end_at`, хотя занятия
  обычно имеют стандартную длительность. Ошибочный диапазон влияет на календарь
  и проверку конфликтов.
- **Решение пользователя:** хранить `start_at`, `duration_minutes` и `end_at`;
  каноническими считать начало и длительность, а окончание всегда рассчитывать
  backend. База запрещает рассинхронизированные значения. Для каждого типа
  `group/individual/split` в `SessionTypeConfig` задаётся стандартная
  длительность, начальное значение — 60 минут. Основная форма показывает начало,
  длительность, рассчитанное окончание и быстрые варианты 30/45/60/90/120 минут.
  Допустимый диапазон — 15–480 минут с шагом 5. Скрытый режим «Указать время
  окончания» пересчитывает длительность. Недельные планы также используют начало
  и длительность. API принимает `duration_minutes`; для обратной совместимости
  временно принимает `end_at`, вычисляя длительность, а при передаче
  несовместимых значений возвращает ошибку. Пересечения продолжают проверяться
  по сохранённым `start_at/end_at`. Старые записи автоматически нормализуются до
  ближайших пяти минут и диапазона 15–480 с пересчётом окончания.
- **Статус:** исправлено.
- **Результат:** backend канонически рассчитывает `end_at` из начала и длительности,
  типы занятий имеют стандартную длительность, формы показывают расчёт и быстрые варианты.
