# SwimCRM UI rework backlog

Дата фиксации: 2026-07-21

Цель документа: держать под рукой рабочий список доработок интерфейса после отказа от NocoBase и перехода на собственную админку. Главный принцип: если элемент выглядит как рабочий элемент интерфейса, он должен быть кликабельным или явно не выглядеть интерактивным.

## Короткий вывод

Текущая custom UI-админка уже лучше NocoBase-заглушки, но это еще не готовый продуктовый интерфейс. Основные проблемы сейчас:

- не все карточки, строки, имена и счетчики ведут в конкретный объект или нужный фильтр;
- часть экранов все еще содержит польские подписи и технический текст вида "Dane z API";
- часть переходов слишком плоская: открывается раздел, но не открывается нужный клиент, занятие, группа или финансовый контекст;
- клиентский и тренерский порталы требуют отдельной проверки на runtime-баги;
- нужно полностью исключить возврат старого demo/mock layout после обновления страницы;
- финансовые действия должны быть доступны прямо из карточки клиента.

## P0 - критично перед продолжением разработки

### 1. Убрать все остатки demo/mock fallback

Проблема: при ошибке подключения экрана или загрузки данных пользователь не должен видеть старый дизайн-макет или mock UI.

Что сделать:

- проверить все fallback-ветки рендера;
- заблокировать возврат legacy design bundle как рабочего экрана;
- вместо старого макета показывать понятное состояние загрузки, ошибки или пустого списка;
- добавить smoke-тест на refresh страницы.

Критерий приемки:

- после перезагрузки страницы всегда остается новая рабочая оболочка;
- старый mock layout нигде не появляется;
- если данные не загрузились, пользователь видит нормальное сообщение и кнопку повторить.

### 2. Починить клиентский и тренерский порталы

Проблема: в коде есть признаки возможных runtime-багов на экранах профиля клиента и посещаемости тренера.

Что сделать:

- пройти все пункты меню роли "Клиент";
- пройти все пункты меню роли "Тренер";
- исправить неинициализированные состояния загрузки/ошибок;
- добавить smoke-тесты на открытие всех пунктов меню.

Критерий приемки:

- ни один пункт меню клиента и тренера не падает;
- каждый экран открывается после refresh;
- нет console/runtime ошибок.

### 3. Полная русификация интерфейса

Проблема: админка частично на русском, но много польских подписей: Klienci, Platnosci, Zamknij, Utworz, Dane z API.

Что сделать:

- заменить пользовательские подписи на русский;
- убрать технические описания API из UI;
- привести статусы, кнопки, пустые состояния и ошибки к одному языку;
- оставить технические endpoint-названия только в коде и документации.

Критерий приемки:

- обычный пользователь не видит польский/технический текст;
- все пункты меню, кнопки, таблицы и сообщения понятны на русском.

### 4. Финансовые действия прямо из карточки клиента

Проблема: ручная оплата добавлена, но финансовый блок клиента должен закрывать основные операции администратора.

Что сделать:

- добавить ручное начисление;
- добавить выдачу абонемента;
- добавить продление абонемента;
- добавить заморозку абонемента;
- добавить ручную корректировку остатка занятий;
- показывать способ оплаты: cash, bank transfer, IBAN;
- запретить удаление истории оплат, посещений и финансовых событий.

Критерий приемки:

- админ может открыть клиента и выполнить основные финансовые действия без перехода в общий раздел платежей;
- история оплат остается неизменяемой в смысле удаления;
- каждое чувствительное действие логируется.

### 5. Smoke-тест кликабельности меню

Проблема: нельзя больше допускать ситуацию "кнопка есть, но ничего не работает".

Что сделать:

- тест: админ открывает все пункты меню;
- тест: тренер открывает все пункты меню;
- тест: клиент открывает все пункты меню;
- тест: refresh не возвращает старый макет;
- тест: из карточки клиента можно добавить оплату;
- тест: клик по занятию открывает состав.

Критерий приемки:

- тесты проходят локально и в CI;
- каждый новый пункт меню обязан иметь тест открытия.

## P1 - основной рабочий UX админки

### 6. Пульт администратора

Что улучшить:

- KPI "Занятия" открывает расписание с фильтром на ближайшие/сегодня;
- KPI "Клиенты" открывает базу клиентов;
- KPI "Тренеры" открывает команду;
- KPI "Должники" открывает список должников;
- предупреждение о платежах открывает платежи с фильтром "ожидают подтверждения".

Критерий приемки:

- клик по счетчику всегда открывает полезный контекст, а не просто декоративный раздел.

### 7. Клиенты

Что улучшить:

- имя клиента/ребенка ведет в карточку клиента;
- группа в строке клиента ведет в карточку группы;
- баланс/абонемент ведет во вкладку финансов клиента;
- добавить быстрый поиск по имени, телефону, email;
- формы создания клиента и участника держать за кнопками/попапами, не раскрывать постоянно.

Критерий приемки:

- пользователь может перейти от списка клиентов к любому важному связанному объекту за один клик.

### 8. Карточка клиента

Что улучшить:

- верхняя панель быстрых действий: оплата, начисление, абонемент, корректировка, напоминание;
- участники кликабельны и редактируемы;
- вкладка посещений открывает конкретное занятие;
- вкладка платежей показывает метод оплаты и статус;
- вкладка абонементов показывает остаток, дату начала, дату окончания, дату оформления.

Критерий приемки:

- карточка клиента становится основным рабочим экраном администратора по клиенту.

### 9. Тренеры

Что улучшить:

- сделать карточку тренера вместо одного inline-edit;
- показывать расписание тренера;
- показывать группы тренера;
- показывать историю занятий;
- добавить расчет зарплаты;
- добавить настройки ставок по типам занятий.

Критерий приемки:

- клик по тренеру открывает полноценный профиль тренера.

### 10. Группы

Что улучшить:

- сделать карточку группы;
- показывать состав группы;
- показывать расписание группы;
- показывать тренера и вместимость;
- добавить быстрые действия добавить/убрать участника;
- счетчик участников открывает состав.

Критерий приемки:

- группа становится рабочим объектом, а не просто строкой редактирования.

### 11. Расписание

Что улучшить:

- добавить календарный UX: день, неделя, месяц;
- клик по занятию открывает занятие;
- клик по счетчику участников открывает состав;
- фильтры: дата, локация, тренер, группа, статус;
- создание занятия, шаблона и генерация расписания открываются через кнопки/попапы.

Критерий приемки:

- расписание можно использовать как главный операционный экран дня.

### 12. Занятие

Что улучшить:

- имя участника открывает профиль клиента;
- добавить "отметить всех присутствовали";
- добавить причины отмены/переноса;
- добавить историю изменений;
- поддержать отдельные типы individual и split;
- показать списание занятия: -1 или 0.

Критерий приемки:

- админ может полностью управлять составом и посещаемостью занятия из одного экрана.

### 13. Платежи

Что улучшить:

- фильтры: ожидают, подтверждены, отклонены, cash, bank transfer;
- клик по клиенту/ребенку открывает карточку клиента;
- быстрое подтверждение/отклонение;
- редактирование комментария и метода оплаты только через чувствительное действие;
- история платежей не удаляется.

Критерий приемки:

- платежи можно быстро разобрать без ручного поиска клиента.

### 14. Должники

Что улучшить:

- клик по строке/имени открывает карточку клиента;
- кнопка отправки напоминания;
- фильтры по сумме, сроку, группе;
- история напоминаний;
- отметка "связались" или "нужно повторить".

Критерий приемки:

- админ видит не просто список долгов, а рабочий инструмент взыскания/напоминаний.

## P2 - тренерский кабинет

### 15. Мои занятия

Что улучшить:

- вся строка занятия кликабельна;
- фильтры: сегодня, неделя, группа, статус;
- отмененные занятия визуально отличаются, но не исчезают.

Критерий приемки:

- тренер быстро открывает нужное занятие и отмечает посещаемость.

### 16. Посещаемость тренера

Что улучшить:

- массовая отметка;
- понятные статусы "был", "не был", "уважительная", "перенос";
- имя ребенка кликабельно, если тренеру разрешено видеть ограниченную карточку;
- показывать экстренные контакты только если это разрешено политикой доступа.

Критерий приемки:

- тренер может отметить группу за минимальное число кликов.

### 17. Мои группы

Что улучшить:

- карточки групп должны открываться;
- внутри группы показывать состав и ближайшие занятия;
- счетчик учеников открывает состав.

Критерий приемки:

- в тренерском кабинете нет карточек, которые выглядят кликабельными, но ничего не делают.

### 18. История тренера

Что улучшить:

- клик по прошлому занятию открывает состав и отметки;
- фильтр по периоду;
- фильтр по группе.

Критерий приемки:

- тренер может быстро проверить прошлые занятия.

### 19. Главная клиента

Что улучшить:

- карточка абонемента открывает абонемент;
- карточка баланса открывает платежи;
- если есть долг, показывать понятное действие "отправить подтверждение оплаты".

Критерий приемки:

- главная клиента ведет к действиям, а не просто показывает данные.

### 20. Расписание клиента

Что улучшить:

- показывать тренера, место, группу, статус;

### 21. Абонемент клиента

- показать остаток занятий;

Критерий приемки:

### 22. Платежи клиента

- файл подтверждения;

- история платежей.

Критерий приемки:

### 23. История клиента

Что улучшить:

- занятия кликабельны;

- фильтр по ребенку;
- фильтр по периоду.

Критерий приемки:

### 24. Профиль клиента

Что улучшить:

- участники/дети кликабельны;
- данные контактов редактируемы;
- соцсети и каналы связи видны в одном месте;
- настройки языка доступны в профиле.

Критерий приемки:

### 25. Согласия

Что улучшить:

- русские названия согласий;
- понятное описание каждого согласия;
- дата выдачи/отзыва;
- версия политики.

Критерий приемки:

- клиент понимает, что именно он подтверждает или отзывает.

## P4 - сквозные улучшения

### 26. URL-состояние и refresh

Что сделать:

- хранить текущий экран и выбранный объект в URL;
- refresh не должен терять карточку клиента/занятия;
- back/forward браузера должны работать ожидаемо.

Критерий приемки:

- можно отправить ссылку на конкретного клиента или занятие.

### 27. Глобальный поиск

Что сделать:

- поиск по клиентам, детям, телефонам, email, группам;
- быстрый переход к объекту;
- поиск доступен из верхней панели.

Критерий приемки:

- админ находит клиента или занятие без ручного хождения по меню.

### 28. Единые empty/loading/error states

Что сделать:

- для пустого списка показывать понятное действие;
- для загрузки показывать skeleton или аккуратный loader;
- для ошибки показывать причину и кнопку повторить.

Критерий приемки:

- пустой экран не выглядит как сломанный интерфейс.

### 29. Права доступа и аудит

Что сделать:

- родители видят только своих детей;
- тренер видит только разрешенные данные;
- финансовые и чувствительные действия требуют аудита;
- удаление истории оплат и посещений запрещено.

Критерий приемки:

- интерфейс не показывает лишние данные и не дает опасных действий без следа.

### 30. CI evidence

Что сделать:

- build frontend;
- backend tests;
- smoke frontend;
- smoke live URL;
- сохранить результаты в release evidence.

Критерий приемки:

- перед деплоем есть доказательство, что ключевые сценарии работают.

## Рекомендуемый порядок работы

1. Закрыть P0: fallback/mock, runtime-баги, русификация, базовые smoke-тесты.
2. Довести админский core: клиент, расписание, занятие, платежи, должники.
3. Довести тренерский кабинет.
4. Довести клиентский кабинет.
5. Добавить URL-состояние, глобальный поиск, polish и расширенный CI evidence.

- Django admin не требуется для ежедневных справочников, уведомлений, ставок, локализации и просмотра журналов;

- mobile viewport не имеет горизонтального переполнения, а меню ролей открывается из верхней крошки без лишней кнопки выхода.
