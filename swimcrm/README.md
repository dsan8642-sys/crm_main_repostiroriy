# CRM школы плавания — ядро (Фаза 1 / MVP)

Реализовано на **Django** (предпочтителен по ТЗ) как **модульный монолит**. Деньги —
целые минорные единицы + ISO-код валюты (никаких `float`). БД по умолчанию SQLite для
быстрого локального запуска и тестов; в проде — PostgreSQL.

## Что сделано (и покрыто тестами)

Все 10 критичных бизнес-правил раздела 3 ТЗ реализованы сервисами и ограничениями БД,
и доказаны backend-тестами (`python manage.py test tests`):

| Правило ТЗ | Где | Тест |
|---|---|---|
| 0. Деньги = минорные единицы + валюта, без float | `common/money.py` | `MoneyRule` |
| 1. Журнал движений (не счётчик), неизменяемый | `subscriptions.SessionLedgerEntry`, `.services` | `LedgerRule` |
| 2. Списание по статусу (Присут./Отсут. → −1; Уваж./Перенос → 0) | `attendance.services.set_attendance` | `AttendanceDeductionRule` |
| 3. Заморозка = интервал, сдвигает дату окончания, хранит историю | `subscriptions.FreezePeriod`, `.services.freeze_subscription` | `FreezeRule` |
| 4/5. Шаблон→занятия, правки серии/одного, контроль конфликтов | `scheduling.services` | `ScheduleConflictRule` |

Полная доменная модель раздела 2 присутствует. Интерфейс администратора — встроенная
Django-админка (все сущности зарегистрированы; журналы движений и действий — read-only).

## Ключевые инженерные решения

- **Списание при смене статуса не редактирует прошлые записи** — журнал append-only,
  поэтому смена «Присутствовал»→«Уваж.» постит компенсирующую запись `CORRECTION (+1)`.
- **Гонки при записи на занятие** закрыты `select_for_update` на Session + unique
  `(session, student)`. Двойное бронирование тренера на PostgreSQL закрыто
  GIST exclusion-constraint (`scheduling/migrations/0002...`), на SQLite — app-check.
- **Баланс считается из Charge − подтверждённые Payment**, а не из платежей. Статусы
  «Частично оплачено»/«Просрочено» вычисляются FIFO-аллокацией (`charge_statuses`).
- **Безлимитный абонемент** не трогает журнал (нет счётчика занятий) — посещения при
  этом всё равно фиксируются в `AttendanceRecord`.

## Запуск

    pip install -r requirements.txt
    python manage.py migrate
    python manage.py seed_demo      # демо-данные (admin/coach/parent)
    python manage.py createsuperuser   # или войдите: admin / Admin!2026pass
    python manage.py runserver      # админка: http://127.0.0.1:8000/admin/
    python manage.py test tests     # прогон бизнес-правил

Ночная задача (правило 10) — `python manage.py purge_receipts` (повесить на Celery beat).

Для PostgreSQL задайте `POSTGRES_DB/USER/PASSWORD/HOST` — тогда включится и
exclusion-constraint против гонок в расписании.

## Вопросы к заказчику — РЕШЕНЫ (детали в `../DECISIONS.md`)

1. Остаток занятий при продлении/истечении (раздел 5.3) — **не сгорает, всегда переносится**;
   по истёкшему-непродлённому абонементу с остатком ходить можно (проверка по остатку журнала).
2. Хранение `Payment` — **бессрочно** (минимум: дата+сумма); бухотчётность вне CRM; файл чека
   удаляется через 30 дней (`RECEIPT_RETENTION_DAYS`). Совпадает с текущей реализацией.
3. Телефон — **один на семью** (`ParentAccount.phone`, уникальный); у ученика своего телефона
   нет. Реализовано: `Student.phone` удалён, `emergency_contact_phone` сохранён.

## Не входит в это ядро (Фазы 2–3 по разделу 9)

- SPA-порталы клиента и тренера (React/Vue) + REST/GraphQL API — здесь только доменное
  ядро и админка. Сервисный слой готов к тому, чтобы навесить API.
- Доставка уведомлений (Email/Telegram/SMS/Push), планировщик на Celery/BullMQ — модели
  правил/шаблонов/лога и SMS-валидация готовы; отправка — заглушка.
- Отчёты и импорт/экспорт .xlsx/CSV (5.9/5.10) — точка расширения (openpyxl в зависимостях).
- 2FA для админа, блокировка после серии неудачных входов — hardening раздела 6.

`notifications`. Покрыто общим backend suite (`python manage.py test tests`).

| Модуль ТЗ | Что реализовано | Где | Тесты |
|---|---|---|---|
| 5.5 Должники / «Скоро оплата» | Должники (просрочка / истёкший абонемент / отриц. баланс); «скоро оплата» по окну дней и по остатку занятий; фильтры 1/3/7/14/30 | `analytics/debtors.py` | `DebtorsRule` |
| 5.9 Отчёты | Доход за период / по группам / по тренерам (кассовый метод — подтверждённые платежи), неоплаченные счета; посещаемость по клиенту/группе/тренеру | `analytics/reports.py` | `ReportsRule` |
| 5.9/5.10 Экспорт | Выгрузка `.xlsx` (Arial, жирная закреплённая шапка) и CSV (UTF-8 BOM, `;`) | `analytics/exporters.py`, `dataio/exports.py` | `ImportRule` |

## Ключевые решения Фазы 2

- **Тайминг не захардкожен**: правило = `event_type + offset_minutes + channel + template`;
  планировщик считает `trigger = reference + offset` и шлёт, когда `now >= trigger`.
- **Идемпотентность**: `NotificationLog.dedup_key` (уникальный) — один и тот же повод не
  отправляется дважды, сколько бы раз ни дёргали планировщик.
- **Согласия (RODO)**: Email и SMS шлются только при активном `Consent`; Telegram — при
  наличии `chat_id` и отсутствии отзыва. Отписка = отзыв согласия.
- **Ретраи**: мягкая ошибка доставки оставляет запись в `QUEUED` и растит `retries`;
  после `MAX_RETRIES` — статус `FAILED`.
- **Импорт безопасен**: предпросмотр без записи; commit в одной транзакции (частичный
  импорт невозможен); `ImportBatch.rollback()` откатывает применённый импорт целиком.
- **Доход — кассовый метод**: считается по подтверждённым платежам (как зафиксировано в 5.9).

## Новые команды (точки для Celery beat / cron)

    python manage.py run_notifications   # планировщик уведомлений (каждые 5–15 мин)
    python manage.py purge_receipts      # авто-удаление чеков (правило 10, ночью)

Экспорт/импорт и отчёты вызываются из кода (`analytics.reports`, `dataio.exports`,
`dataio.importer`) — готовы к тому, чтобы навесить админ-экшены или REST-эндпоинты.
