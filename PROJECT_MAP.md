# Карта проекта SwimCRM

Этот файл — короткий навигатор по действующему коду. Бизнес-детали находятся в
спецификациях, а полный перечень HTTP-маршрутов — в `swimcrm/portal/urls.py` и
OpenAPI. При расхождении документа с кодом источником истины является код и
автоматические тесты; карту после этого необходимо обновить.

## Быстрый маршрут для новой задачи

| Задача | Читать здесь | Затем открыть в коде |
|---|---|---|
| Правило или данные | разделы 4, 6–7; нужный пункт `DECISIONS.md` | `swimcrm/<domain>/services.py`, `models.py`, тесты |
| API | разделы 4, 6–7; `docs/API_CONTRACT.md` по необходимости | `swimcrm/portal/urls.py`, нужный `*_views.py`, `openapi.py` |
| Экран или навигация | разделы 3, 5–6 | `frontend/src/app/runtime.jsx`, нужный экран, `AppShell.jsx` |
| Общий дизайн | разделы 2, 5–6; `docs/DESIGN_SYSTEM.md` | `design/`, затем скрипты синхронизации |
| Запуск или выпуск | раздел 8; `DEV.md` либо `docs/OPERATIONS.md` | нужный скрипт в `scripts/` |

Открывайте только относящиеся к задаче разделы и файлы. Текущее состояние
рабочего дерева проверяйте через Git: этот документ не хранит статус задач.

## 1. Архитектура в одном экране

```text
Browser
  │
  ├─ React SPA: frontend/src/main.jsx → App.jsx → AppShell.jsx
  │                                      │
  │                                      ├─ runtime.jsx: роли и навигация
  │                                      └─ app/screens/: страницы
  │
  └─ /api/*
       ↓
     config/urls.py → portal/urls.py → portal/*_views.py
                                         ↓
                               domain services.py
                                         ↓
                                  domain models.py
                                         ↓
                              SQLite dev / PostgreSQL prod

Background work: management commands или Celery → */tasks.py → services.py
```

Основной принцип: HTTP и сериализация находятся в `portal/`, бизнес-правила —
в доменных сервисах, состояние — в моделях. React не должен повторять правила,
которые сервер обязан гарантировать.

## 2. Каталоги верхнего уровня

| Путь | Назначение | Источник истины |
|---|---|---|
| `swimcrm/` | Django-приложение, доменные модули и backend-тесты | Да |
| `frontend/` | React SPA и frontend-тесты | Да |
| `design/` | Токены, компоненты и исходники дизайн-системы | Да |
| `frontend/src/design/` | Runtime-копия дизайн-системы для Vite | Генерируется из `design/` |
| `scripts/` | Локальные проверки, сборка, release и operations | Да |
| `docs/` | Спецификации, инструкции и справочные материалы | См. `docs/README.md` |
| `audit/` | Run-specific QA evidence и локальная синтетическая среда | Нет, не runtime-код |

`swimcrm/audit/` — это Django-модуль журнала аудита. Его нельзя путать с
корневым `audit/`, где лежат QA-материалы.

## 3. Навигация интерфейса

SPA использует query-параметры, а не отдельный router-пакет:

```text
/?role=<role>&view=<view>&client=<id>&session=<id>&group=<id>...
```

Разбор и запись URL находятся в `frontend/src/app/AppShell.jsx`. Разрешённые
страницы и меню определены в `frontend/src/app/runtime.jsx`.

Светлая и тёмная палитры — `design/tokens/themes.css`. Переключатель всех ролей
находится в `AppShell.jsx`: в раскрытом меню компьютера — слева от языка,
в меню телефона — справа; в свёрнутом боковом меню тема расположена над языком.
`app/theme.js` хранит
выбор в браузере (`swimcrm.theme`),
`main.jsx` применяет его до рендера. Оформление рабочего стола — `app/theme-layout.css`.
Цвета расписания адаптируются через `schedulePalette.js`, сохраняя выбранные ключи цветов.
Появление и закрытие всплывающих элементов координирует `app/usePresence.js`; общие анимации находятся в `app/ops-redesign.css`, а подтверждения дизайн-системы — в `design/components/feedback/Dialog.jsx`.
Тёмная палитра усиливает текст и цветные состояния; фон второстепенных кнопок
задаётся токеном `--action-secondary-background` в `design/tokens/themes.css`.
Иконки разделов всех ролей задаются в `runtime.jsx`, а их исходники — в
`design/assets/icons.jsx`; главное действие страницы использует тот же образ,
что соответствующий раздел (календарь, кошелёк, абонемент, группа).
Кнопки создания тренера и группы используют `TrainerPlus` и `GroupMembersPlus`;
разделы меню — `Trainer` и `GroupMembers`.
Копирование периода расписания использует `Copy`; иконки быстрых действий
расписания занимают одинаковую колонку в `ops-redesign.css`.

Общее меню дополнительных действий — `ActionPopover` в `app/EntityListPrimitives.jsx`, стили `.ops-entity-actions-trigger` в `app/ops-redesign.css`: горизонтальные точки, нейтральный фон, квадратная кнопка 36 px (44 px на сенсорных экранах), общие состояния наведения, открытия и фокуса. Используется в карточках и таблицах клиентов, групп, тренеров, платежей, должников и абонементов.

На широком экране все пять финансовых действий карточки клиента стоят в одной строке; на узком экране пополнение и продажа абонемента доступны рядом с меню «Ещё», которое содержит остальные действия.
Действия с аккаунтом на широком экране показаны кнопками в две строки в шапке карточки клиента; на узком экране они находятся в меню действий.

### Администратор

| `view` | Экран | Основная область API |
|---|---|---|
| `overview` | Рабочий стол: ближайшее занятие, быстрые оплата/создание клиента/индивидуальная и сплит-тренировка, два KPI, карточки занятий в две колонки (одна на телефоне) | `/api/admin/dashboard/`, `/api/admin/upcoming/`, `/api/admin/payments/` |
| `clients` | Клиенты: вкладки списка и чёрного списка, общий поиск и раскрываемые фильтры | `/api/admin/clients/` |
| `clientDetail` | Компактная карточка клиента: сводка совмещена с навигацией (баланс в платежах, остаток и срок абонемента, участники и посещения), контакты видны, участник выбирается списком только при нескольких, редкие финансовые действия — в кнопке «Ещё», управление аккаунтом — в меню; история и независимое исправление дат абонемента, заморозка/остаток, мобильные вкладки платежей; абонемент в посещениях, выборе оплаты и заголовке истории обозначается названием и датой начала; в посещениях «Изменить» и «Фильтры» стоят в одной строке; фильтры раскрываются отдельной карточкой с анимацией и сохраняют выбор при сворачивании; фильтры с множественным выбором по источнику списания и статусу («Не был» включает уважительные пропуски): варианты внутри фильтра объединяются, два фильтра пересекаются; выбор записей по кнопке «Изменить» для переноса между счётом и абонементом; форма изменения оплаты и число выбранных записей находятся в отдельной карточке с анимацией; смена фильтра снимает выбор записей | `/api/admin/clients/{id}/`, `/api/admin/subscriptions/{id}/update/`, `/api/admin/participants/{id}/attendance/payment/`, participant endpoints |
| `schedule` | Расписание без отдельного дневного режима; на компьютере режимы недели и месяца, на телефоне занятия выбранного дня недели и перелистывание периодов стрелками; месяц показан календарной сеткой со всеми занятиями каждого дня без скрытия, внутри занятия время и переносимое название группы стоят в две строки, при средней ширине сетка в три колонки, на телефоне — в две; узкие карточки недели показывают начало и длительность с иконкой часов отдельными строками, широкие — диапазон времени; название группы и тип занятия оформлены менее заметно, чем время, а иконки тренера и места не сжимаются длинным текстом; назначенные цвета занятий и групп одинаковы в обеих темах во всех местах использования | `/api/admin/schedule/*` |
| `attendance` | Посещаемость занятия; сведения о выбранном занятии сворачиваются в строку, повторное нажатие на отметку снимает её | schedule attendance GET/POST/DELETE endpoints |
| `groups` | Группы; выбор из готовой палитры или собственного HEX-цвета, который одинаково отображается в светлой и тёмной темах и занятиях группы | `/api/admin/groups/` |
| `trainers` | Тренеры | `/api/admin/trainers/` |
| `payments` | Платежи | `/api/admin/payments/` |
| `debtors` | Должники | `/api/admin/debtors/` |
| `subscriptions` | Абонементы | `/api/admin/subscriptions/` |
| `settings` | Настройки и операции: категории и пункты слева на десктопе, пошаговый выбор на телефоне (`AdminSettingsScreen.jsx`); «Инструкции» → сабкатегории «Клиенты», «Расписание», «Группы», «Тренеры»; выбор темы открывает только её скриншот-инструкцию (`GuideScreen.jsx`); отчёты и их мобильная раскладка — `AdminReportsPanel.jsx`/`.css` | `/api/admin/settings/*`, reports, import, payroll, notifications, system |

В карточке клиента подсветка выбранного раздела расходится от точки нажатия
(с клавиатуры — от центра), предыдущая плавно гаснет; содержимое появляется плавно. Мобильные
вкладки пополнений и начислений используют скользящий индикатор. Анимации
отключаются при `prefers-reduced-motion: reduce`.

В локальной разработке администратору доступна панель оформления поверх любого экрана:
`frontend/src/app/AppearanceEditor.jsx` → `/api/dev/appearance/` → `design/appearance.json`
и `design/tokens/appearance.css`. Панель активна только при DEBUG и локальном доступе.
Режим выбора элемента сохраняет свойства отдельного узла в `overrides`, с привязкой
к роли, экрану и пути элемента в DOM; `AppShell.jsx` задаёт `data-appearance-route`.
Текстовые замены из runtime-копии `frontend/src/design/appearance.json` применяет
`app/appearanceText.js` только при совпадении исходной надписи.
Локальный редактор показывает скрываемую структуру DOM выбранной страницы и
позволяет выбирать вложенные элементы из списка. Список прокручивается внутри
своей панели; выбранные элементы можно скрыть, убрать из раскладки и вернуть.
Редактор добавляет простые текстовые элементы и блоки, а также копирует и
вставляет их текст с заданными свойствами. Добавленные элементы хранятся в
`blocks` файла `design/appearance.json`; `app/appearanceBlocks.js` восстанавливает
их на выбранном экране.

`clientDetail` и `attendance` — контекстные страницы, поэтому в основном меню
они не показываются. Внутри настроек находятся каталог, уведомления, зарплата,
локализация, контроль/импорт и отчёты.

## 4. Backend-модули

| Модуль | Отвечает за |
|---|---|
| `config` | Django settings, корневые URL, ASGI/WSGI, Celery |
| `accounts` | Пользователей, роли, доступ, активацию, 2FA, лимит попыток и защиту от повтора TOTP |
| `students` | Аккаунты клиентов, участников и членство в группах |
| `catalog` | Тренеров, группы, локации и типы занятий |
| `scheduling` | Занятия, расписание, вместимость, лист ожидания и конфликты; транзакционные операции самозаписи блокируют только строку занятия |
| `scheduling.SessionTypeConfig` | Системные и пользовательские типы занятий; `base_type` сохраняет базовые правила, а `Session.session_type_config` — выбранный тип |
| `attendance` | Посещения и их влияние на абонементы/начисления; `change_attendance_payment` атомарно меняет источник списания и по явному выбору включает учёт исторических посещений; для выбора абонемента `subscriptions.services.can_assign_attendance` проверяет: срок не истёк ИЛИ есть занятия; `set_attendance` сохраняет ручной выбор при изменениях отметки |
| `subscriptions` | Типы и экземпляры абонементов, остатки, даты окончания, продление и заморозку |
| `billing` | Начисления и платежи привязаны к участнику для аудита; `family_balance(s)` и `family_charge_statuses` объединяют деньги по `ParentAccount`, сохраняя личные абонементы и посещаемость |
| `notifications` | Шаблоны, правила, отправку, повтор и quiet hours; `deliver` повторно проверяет согласие канала непосредственно перед вызовом внешнего backend |
| `payroll` | Схемы, ставки, назначения и расчётные периоды |
| `localization` | Языки и серверный словарь переводов |
| `audit` | Неизменяемый журнал значимых действий |
| `analytics` | Агрегации и аналитические данные |
| `dataio` | Preview/commit/rollback импорта и экспорт |
| `portal` | HTTP API для admin, trainer и client поверх доменных модулей |
| `tests` | Интеграционные, контрактные и бизнес-тесты backend |

Для изменения правила сначала ищите соответствующий `services.py`, затем
`models.py` и тесты. Не размещайте новое бизнес-правило только во view.

В резервном Django admin посещения, абонементы, журнал занятий, начисления,
платежи, события платежей и подтверждающие файлы доступны только для просмотра
через `common/admin.py`. Продажа, продление и финансовые изменения выполняются
через основной интерфейс CRM; прямое действие продления в Django admin удалено.

Операции, меняющие остаток занятий, блокируют участника перед чтением остатка:
посещаемость, покупка, продление и ручная корректировка. При продлении исходный
абонемент перечитывается под блокировкой. Массовые отметки блокируют участников
по ID; финансовый импорт сначала блокирует известные занятия, затем участников.

## 7. Данные и запрос

Типичный UI-запрос проходит так:

```text
Screen → api.js → portal URL/view → domain service → model/database
       ← mapper/contract ← JSON response ← serializer/helper
```

Ошибки полей должны пройти обратно в `error.fieldErrors`; не заменяйте их одним
общим сообщением. Денежные значения передаются в minor units там, где это
зафиксировано контрактом. Финансовые записи принадлежат участнику, а не группе.

## 8. Тесты

| Набор | Путь | Команда |
|---|---|---|
| Backend | `swimcrm/tests/` и тесты доменных apps | `cd swimcrm; .\.venv\Scripts\python.exe manage.py test tests --noinput` |
| Frontend unit | `frontend/test/` | `cd frontend; npm.cmd test` |
| Browser/E2E | `frontend/tests/` | `cd frontend; npm.cmd run test:smoke` |
| Production build | `frontend/` | `cd frontend; npm.cmd run build` |
| Full release gate | `scripts/` | `.\scripts\release-check-full.ps1` |

`frontend/test/` и `frontend/tests/` не дублируют друг друга: первый каталог —
unit-тесты Node, второй — Playwright.

Функциональные Playwright-сценарии должны искать элементы по `data-testid`,
стабильным атрибутам и данным тестовых записей, а не по переведённым подписям.
Текстовые проверки оставлены сценариям локализации; браузерный набор должен
проходить с украинским языком по умолчанию.
Для языковой матрицы Playwright можно задать `SWIMCRM_PLAYWRIGHT_LOCALE`
(`uk`, `ru`, `pl`, `en`); параметр заполняет только начальное состояние
браузера для тестовых администраторов и клиентов.
